# Mini NPU Simulator

외부 라이브러리 없이 Python 반복문만으로 MAC(Multiply-Accumulate) 연산을 구현하고, Cross(십자가)와 X 패턴을 판별하는 콘솔 애플리케이션입니다.

3×3 데이터를 직접 입력하는 모드와 `data.json`의 5×5, 13×13, 25×25 데이터를 일괄 분석하는 모드를 제공합니다. 각 패턴의 점수와 판정 결과를 출력하고, 크기별 평균 연산 시간을 측정해 입력 크기와 연산량의 관계를 확인할 수 있습니다.

> 📘 과제의 전체 배경과 요구사항은 [미션 가이드](mission/README.md)에서 확인할 수 있습니다.

## 주요 기능

- 3×3 필터 2개와 패턴을 콘솔에서 직접 입력
- 행·열 개수 및 숫자 형식 검증 후 잘못된 행 재입력
- `data.json`의 필터와 패턴 스키마 및 크기 검증
- `+`, `cross`, `x` 라벨을 `Cross`, `X`로 정규화
- 반복문으로 위치별 곱셈과 누적 합산(MAC) 수행
- `epsilon = 1e-9` 기준으로 부동소수점 동점 처리
- 케이스별 `PASS`/`FAIL` 및 실패 사유 출력
- 3×3, 5×5, 13×13, 25×25 연산 성능 측정
- 전체 테스트 수, 통과 수, 실패 수 요약

## 동작 원리

MAC 연산은 패턴과 필터에서 같은 위치의 값을 곱한 뒤 모두 더합니다.

```text
score = Σ(pattern[row][column] × filter[row][column])
```

Cross 필터 점수가 더 높으면 `Cross`, X 필터 점수가 더 높으면 `X`로 판정합니다. 두 점수의 차이가 `1e-9`보다 작으면 부동소수점 오차로 인한 잘못된 우열 판정을 막기 위해 `UNDECIDED`로 처리합니다.

### 모드 1: 사용자 입력

필터 A, 필터 B, 패턴을 각각 세 줄씩 입력합니다. 각 줄에는 공백으로 구분한 숫자 3개가 필요합니다.

```text
필터 A
0 1 0
1 1 1
0 1 0

필터 B
1 0 1
0 1 0
1 0 1

패턴
1 0 1
0 1 0
1 0 1
```

위 예시에서는 A 점수 `1.0`, B 점수 `5.0`이 계산되어 결과가 `B`로 판정됩니다. 점수와 함께 10회 반복 측정한 평균 연산 시간도 출력됩니다.

### 모드 2: data.json 분석

프로젝트에 포함된 `data.json`을 읽어 다음 순서로 처리합니다.

1. 크기별 Cross/X 필터 로드 및 검증
2. 패턴 키에서 크기 추출
3. 패턴과 필터의 크기 및 데이터 형식 검증
4. Cross/X MAC 점수 계산과 결과 판정
5. 예상 라벨과 비교하여 `PASS` 또는 `FAIL` 출력
6. 크기별 성능 표와 전체 결과 요약 출력

## 결과 리포트

예제 `data.json`에는 5×5, 13×13, 25×25 크기의 Cross/X 패턴 총 6개가 포함되어 있습니다. 현재 자동 테스트에서는 6개 케이스가 모두 통과했으며 실패 케이스는 없습니다.

실패가 0개인 첫 번째 이유는 외부 데이터의 `+`와 `cross`를 모두 표준 라벨 `Cross`로 변환하고, 대소문자와 관계없이 `x`를 `X`로 변환하기 때문입니다.

두 번째 이유는 필터 키와 `expected` 값을 같은 표준 라벨로 정규화한 뒤 비교하므로, 표현 방식만 다른 라벨이 잘못된 실패를 만들지 않기 때문입니다.

세 번째 이유는 필터와 패턴을 사용하기 전에 행 수, 열 수, 숫자 여부를 검사하여 잘못된 입력이 MAC 연산에 전달되지 않기 때문입니다.

네 번째 이유는 각 패턴 키의 `size_N_idx`에서 `N`을 추출하고 동일한 크기의 `size_N` 필터를 선택하기 때문입니다.

다섯 번째 이유는 두 점수의 차이가 `1e-9`보다 작을 때 `UNDECIDED`로 처리하여 미세한 부동소수점 오차를 실제 점수 차이로 오해하지 않기 때문입니다.

실패가 발생한다면 원인은 크게 데이터·스키마 문제, 판정 로직 문제, 수치 비교 문제로 나누어 진단할 수 있습니다.

데이터·스키마 문제에는 누락된 `input`/`expected`, 잘못된 키 형식, 숫자가 아닌 원소, 필터와 패턴의 크기 불일치가 포함됩니다.

판정 로직 문제는 올바른 크기의 필터를 선택했는지, MAC 반복문이 모든 `N²` 위치를 정확히 한 번씩 계산했는지 확인하여 진단합니다.

수치 비교 문제는 두 점수가 매우 가까울 때 단순 `==` 또는 `>` 비교를 사용했는지 확인하고, epsilon 정책을 적용해 개선할 수 있습니다.

N×N 패턴 한 개의 MAC 점수를 계산하려면 모든 원소를 방문해야 하므로 곱셈은 `N²`회, 누적 덧셈도 `N²`회 수행됩니다.

따라서 MAC 함수의 시간 복잡도는 `O(N²)`이고, 추가 배열을 만들지 않고 점수만 누적하므로 추가 공간 복잡도는 `O(1)`입니다.

예를 들어 3×3은 9개, 5×5는 25개, 13×13은 169개, 25×25는 625개의 위치를 처리합니다.

입력 한 변의 길이가 커질수록 연산 횟수가 제곱으로 증가하므로 평균 실행 시간도 대체로 증가합니다. 단, 매우 짧은 실행 시간은 운영체제 스케줄링과 측정 오차의 영향을 받을 수 있어 프로그램은 각 크기를 최소 10회 반복 측정한 평균값을 출력합니다.

### 대형 N에서의 시간·메모리 병목과 최적화 우선순위

현재 MAC 함수 자체는 점수 변수만 추가로 사용하므로 **추가 공간 복잡도는 `O(1)`**입니다. 그러나 함수에 전달되는 패턴과 필터를 저장하는 데에는 각각 `O(N²)`의 입력 메모리가 필요합니다. 즉, 추가 작업 공간이 작다는 사실과 전체 데이터의 메모리 사용량이 작다는 의미는 서로 다릅니다.

예를 들어 1000×1000 패턴은 원소가 1,000,000개이며, 필터 한 개와 비교할 때 MAC 연산 1회에 곱셈 약 1,000,000회와 누적 덧셈 약 1,000,000회가 필요합니다. Cross와 X 필터를 모두 계산하면 같은 패턴을 두 번 순회하므로 약 2,000,000개 위치를 처리합니다. 벤치마크를 10회 반복하면 약 20,000,000개 위치를 처리하게 되어 순수 Python 중첩 반복문의 실행 시간이 빠르게 증가합니다.

메모리도 병목이 될 수 있습니다. 원소를 연속된 64비트 실수로만 저장한다고 가정하면 1000×1000 행렬 하나의 원시 데이터는 약 8 MB이지만, 현재처럼 Python의 중첩 리스트와 개별 `float` 객체를 사용하면 리스트와 객체 관리 비용이 추가되어 실제 사용량은 이보다 훨씬 커집니다. 패턴 하나와 필터 두 개를 동시에 보관하면 이 비용도 함께 증가합니다.

대형 입력에는 다음 순서로 최적화를 적용하는 것이 적절합니다.

1. **1차원 평탄화:** 2차원 리스트를 길이 `N²`의 1차원 배열로 바꾸어 행 탐색과 인덱싱 비용을 줄이고 메모리 접근을 단순화합니다.
2. **불필요한 복사 제거:** 검증·변환 과정에서 동일한 대형 행렬을 반복 복사하지 않고, 이미 검증된 필터는 여러 패턴에서 재사용합니다.
3. **한 번의 순회로 두 점수 계산:** 패턴을 한 번 읽는 동안 Cross와 X 점수를 함께 누적하여 패턴 메모리 접근 횟수를 줄입니다.
4. **행 단위 스트리밍 또는 청크 처리:** 전체 패턴을 한꺼번에 메모리에 올리기 어려우면 행 또는 블록 단위로 읽고 부분합을 누적합니다.
5. **반복 횟수 조정:** 대형 N에서는 충분한 측정 정확도를 유지하는 범위에서 벤치마크 반복 횟수를 줄여 과도한 실행 시간을 방지합니다.
6. **병렬화·전용 가속기 검토:** 표준 라이브러리만 사용해야 한다는 과제 제약이 없다면, 여러 필터나 패턴을 독립 작업으로 나누거나 벡터 연산 라이브러리와 GPU/NPU 실행 환경을 검토합니다.

현재 과제는 MAC 원리를 반복문으로 직접 학습하는 것이 목적이므로 NumPy 등의 벡터화는 사용하지 않습니다. 따라서 1000×1000 지원이 필요해질 경우에는 과제 제약 안에서 먼저 **1차원 평탄화, 복사 제거, 두 필터 점수의 동시 누적**을 적용하는 것이 우선입니다.

### CPU 직렬 처리와 NPU 병렬 처리의 병목 분석

현재 구현은 CPU에서 중첩 반복문을 실행하며 각 위치의 곱셈과 누적을 순서대로 처리합니다. 계산량이 `N²`으로 증가하는 데 더해 Python 반복문과 동적 객체 접근 비용까지 발생하므로 N이 커질수록 직렬 처리 시간이 주요 병목이 됩니다.

반면 각 위치의 곱셈은 서로 독립적이므로 여러 연산 장치에서 동시에 계산할 수 있습니다. NPU는 많은 곱셈기를 사용해 다수의 MAC 연산을 병렬로 수행한 뒤 부분합을 합치는 방식에 적합합니다. 또한 여러 필터나 여러 패턴도 서로 독립적으로 배치하여 병렬 처리할 수 있습니다.

| 관점 | CPU 직렬 구현의 주요 병목 | NPU 병렬 구현의 주요 병목 |
|---|---|---|
| 연산 | 반복문에서 MAC를 순차 실행 | 처리 장치 수만큼 MAC를 동시에 실행하지만 마지막 부분합 병합 필요 |
| 메모리 | Python 객체 접근과 캐시 미스 | 연산 장치에 데이터를 충분히 공급하는 메모리 대역폭 |
| 데이터 이동 | 주 메모리 안에서 행을 반복 순회 | CPU 메모리에서 NPU 메모리로 보내는 전송 시간과 비용 |
| 작업 크기 | N이 커질수록 직렬 시간이 `N²`에 비례해 증가 | 입력이 너무 작으면 준비·전송 비용 때문에 병렬 장치 활용률이 낮음 |
| 확장 방법 | 평탄화, 캐시 친화적 순회, 작업 분할 | 타일링, 배치 처리, 필터 재사용, 전송과 연산 중첩 |

NPU를 사용한다고 해서 모든 병목이 자동으로 사라지는 것은 아닙니다. 연산은 빨라져도 메모리 대역폭이 부족하면 연산 장치가 데이터를 기다리게 되고, 작은 입력은 장치 초기화와 데이터 전송 시간이 실제 계산 시간보다 커질 수 있습니다. 많은 병렬 MAC 결과를 하나의 점수로 합치는 **리덕션(reduction)** 단계도 동기화 비용을 만듭니다.

따라서 NPU 설계에서는 데이터를 작은 블록으로 나누어 가까운 메모리에 재사용하는 **타일링**, 여러 패턴을 묶는 **배치 처리**, 한 번 전송한 필터의 **재사용**, 데이터 전송과 계산의 **중첩**을 고려해야 합니다. 이 시뮬레이터는 CPU 직렬 기준 구현이지만, 위치별 곱셈의 독립성과 최종 누적 구조를 통해 어떤 부분을 병렬화할 수 있는지 보여주는 기준 모델 역할을 합니다.

## 데이터 형식

`data.json`은 다음 구조를 사용합니다.

```json
{
  "filters": {
    "size_5": {
      "cross": [[0, 0, 1, 0, 0]],
      "x": [[1, 0, 0, 0, 1]]
    }
  },
  "patterns": {
    "size_5_1": {
      "input": [[1, 0, 0, 0, 1]],
      "expected": "x"
    }
  }
}
```

위 배열은 형식을 간단히 보여주기 위해 일부 행만 표시한 예시입니다. 실제 필터와 패턴은 반드시 `N×N` 크기여야 합니다.
